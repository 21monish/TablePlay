1. PURPOSE
----------

TablePlay is a smart restaurant ordering, service, billing, and table-gaming
platform. A restaurant server runs on a Windows laptop or counter PC. Staff
desktops/phones and customer tablets connect through the restaurant's private
Wi-Fi network. Normal restaurant operation continues locally without internet.

The product contains:

- Laravel web portal, dashboards, REST API, Reverb events, queues, and scheduler.
- Private MariaDB database in the one-click Windows installation.
- One role-based Staff Flutter app for Android and Windows.
- One separate Customer Flutter app for Android table devices.
- TablePlay Server Manager, updater, backup/restore, repair, and uninstaller.
- Optional cloud licensing architecture for commercial subscriptions.


2. REAL RESTAURANT WORKFLOW
---------------------------

1. Admin creates tables, staff accounts, menu categories, dishes, and games.
2. A Customer tablet is paired securely to one table using a single-use QR.
3. The guest opens a visit, browses photos/descriptions, and places an order.
4. Counter confirms or rejects the pending order.
5. Confirmation sends the ticket to Kitchen and starts/restarts that table's
   server-controlled game timer.
6. Kitchen moves the order through Confirmed, Preparing, Ready, and Served.
7. Waiter handles waiter/water/bill requests and can take an order by selecting
   a table when that table has no Customer tablet.
8. Counter generates the bill, accepts cash payment, prints the receipt, and
   closes the visit.
9. Payment/closure stops game access immediately for only that table.

Tables, orders, requests, sessions, and game timers are isolated from each
other. Confirming Table 1 never unlocks Table 2.


3. ROLES
--------

Platform Super Admin:

- Manages commercial restaurants, plans, subscriptions, activation keys,
  installation transfer/deactivation, and offline signed licence files.
- Is separate from restaurant staff access.

Restaurant Admin:

- Dashboard, tables, tablet pairing, staff, menu, games, settings, reports,
  audit history, health, automation, licences, and application updates.

Counter:

- Incoming orders, confirmation/rejection, requests, billing, cash payment,
  receipts, table closure, and game timer extend/stop controls.

Kitchen:

- Live ticket queue, customer instructions, preparation status/timers, ready
  notifications, and served status.

Waiter:

- Guest requests, ready orders, floor/table overview, bill requests, table
  visits, and waiter-entered orders for a selected table.

Customer:

- Menu, photos, descriptions, cart, order status, table services, and games.


4. BRANDING AND MENU IMAGES
---------------------------

TablePlay uses two simple uploaded images:

- Restaurant logo: guest-facing restaurant identity and receipts.
- TablePlay app logo: website/system brand, Staff app, Customer app, and favicon.

Admin can upload both from Restaurant Settings, the first-time setup guide, or
the Staff app. The browser favicon is served through a no-cache endpoint, so a
new app logo replaces the old favicon without waiting for a long browser cache.
Flutter apps refresh branding automatically while preserving login and pairing.

Menu management supports:

- JPEG, PNG, or WebP photo upload up to 5 MB.
- Photo upload/replacement from the website and Staff app.
- Safe deletion of the superseded managed image.
- Short and full descriptions, ingredients, allergens, calories, spice level,
  preparation time, regular/offer price, bestseller/recommended flags, and
  structured customizations.
- Customer tablets refresh menu data/photos automatically (normally within one
  minute), without reinstalling or clearing pairing.

An uploaded logo changes in-app branding, but Android launcher icons and the
Windows EXE icon are signed build-time assets. Changing those operating-system
icons still requires a new signed app build.


5. GAMES
--------

The catalog contains five one-player, four two-player, and four four-player
games. Dinosaur Dash is a native, frame-rate-independent runner. Balloon Ascent
adds smooth drag/keyboard steering, safe-path spike gates, +10 bubbles, progressive
difficulty, Magnet/Slow/Shield power-ups, local best score and server-authorized
result submission. The artwork and branding are original TablePlay assets rather
than copied Google game assets. Every catalog slug opens its intended screen.
Automated Flutter tests cover representative 1-, 2-, and 4-player games plus the
Dinosaur Dash and Balloon Ascent engines, collision rules and controls.

- Access is controlled by the local server per table.
- Games remain locked before Counter confirmation.
- Confirmation starts or restarts the configured duration.
- Counter can extend or stop an active timer.
- Expired timers cannot be resurrected.
- Billing completion stops access immediately.


6. NETWORK AND API
------------------

Default local services:

- Website: http://LAPTOP_IP:8000
- API: http://LAPTOP_IP:8000/api/v1
- Realtime: ws://LAPTOP_IP:8080
- Private installed database: 127.0.0.1:3310 only

All devices must be on the same private router/hotspot and client isolation must
be disabled. Windows should classify the restaurant Wi-Fi as Private. A fixed
DHCP reservation for the server laptop is recommended so app URLs do not change.

8. COMMERCIAL LICENSING
-----------------------

Implemented commercial licensing includes:

- Free Trial, Simple, Best, Pro, and Premium plans with signed features and limits.
- One stable installation UUID and device fingerprint per restaurant server.
- Online activation and synchronization using one-time hashed activation keys.
- Restaurant-generated, self-signed offline activation requests (.tpr).
- Cloud verification of request signature, identity, age, and replay state.
- Ed25519-signed offline licenses (.tpl) bound to the exact request, installation,
  computer, subscription, plan, and monotonic license revision.
- Rejection of tampered, wrong-device, substituted-key, replayed, and stale files
  while preserving the currently valid license.
- Identical re-download of the originally issued signed license.
- Private signing material stored only in the secured Cloud environment.
- Only the public verification key is installed on restaurant servers.
- Current public-key fingerprint:
  ba19a3d79e744b92b07dda9df1109f8f537204663983bc54418f4446c47fa9ba
- Pairing/table/session enforcement through locally verified entitlements.
- Local ordering remains operational without internet while the license is valid.
- Central web/API enforcement for Customer app access, table quotas, games and
  timers, waiter ordering, advanced reports, and automation.
- Trial/Simple/Best/Pro/Premium limits are rechecked on every protected request;
  a downgrade blocks overflow tablets immediately and an upgrade restores them.
- Pairing quota checks are transaction-serialized, secure QR tokens are one-use,
  and legacy public registration/table-code pairing is retired.
- Active games close on billing, unpairing, token revocation, plan removal,
  missing table sessions, or the last server-issued expiry while offline.
- License provenance fails closed: signed cloud/offline records cannot be made
  trusted by changing their database source, status, features, or limits.
- Kitchen completion, billing/payment, verified backups, and game-stop controls
  remain available as safety operations during plan or license transitions.

Offline activation requires no internet or Cloud URL. The .tpr and .tpl files can
be transferred by USB. Offline files use a maximum 30-day renewal lease by default,
so suspension or plan changes take effect no later than the next signed renewal;
a deliberately rolled-back server clock disables signed entitlements. Online
commercial operation still requires a separately secured HTTPS Cloud deployment.

It bundles:

- Portable PHP and private MariaDB.
- TablePlayServer Windows service.

- Server Manager, repair/upgrade, backup/restore, and uninstaller.
- Staff Android 1.9.2 (build 2014).
- Customer Android 1.12.1 (build 2015).
- Staff Windows 1.9.2 (build 14).

Installer hardening through 2.5.6:

- Server Manager launches the temporary uninstaller from the Windows temp
  directory, so it no longer locks C:\Program Files\TablePlay.
- Service Host uses PHP's direct built-in server rather than an artisan parent
  process that could leave duplicate child servers after restart.
- Setup/upgrade creates a fresh public storage link, so logos and menu photos
  work in production installations.
- Development public-storage files are excluded from the installer payload.
- Upgrade always regenerates production PHP configuration and verifies required
  extensions before Laravel migrations run.
- Installer failures include stdout and stderr and are retained in
  logs\setup-commands.log for diagnosis.
- Fresh install, upgrade and rollback are stage-aware; incomplete installations
  can be recovered without treating them as a healthy existing installation.
- Upgrade backups are created only after services and database writes are
  quiesced, and SQL backup checksums are verified before a restore can modify data.
- Critical bundled runtimes, services, apps and server files are verified against
  the build manifest before installed files are touched.
- Success requires database/schema access, Laravel HTTP health, Reverb, queue and
  scheduler supervision, branding API response and a valid public-storage link.
- The exact v2.5.6 staged payload passed an isolated fresh-install followed by an
  in-place-upgrade lifecycle, including retained upload and database verification.
- Interrupted first-time installations are marked before payload copying. On the
  next run, their complete directory is moved intact to
  C:\ProgramData\TablePlay\Recovery before setup restarts; it is never silently
  deleted or mistaken for a completed restaurant.
- Repair recreates a missing Windows service, stops orphaned TablePlay-owned PHP
  processes before replacement, waits for the service's full startup budget and
  validates an older restored version with backward-compatible rollback checks.
- Restaurant MariaDB uses the dedicated tableplay_app account on localhost only;
  setup no longer gives Laravel database-root credentials.
- Setup enables and cryptographically tests Sodium before installation succeeds.
- Setup installs only the trusted Ed25519 public key and removes any legacy private
  signing-key setting from restaurant environments.
- The build uses the verified cached .NET 9.0.19 self-contained runtime so all
  Windows components are reproducible without the stalled partial 9.0.20 pack.

The EXE has a generated SHA-256 file but is not Authenticode-signed unless a
production Windows code-signing certificate is applied after the build. Windows
SmartScreen warnings are expected until TablePlay obtains and uses that
certificate. Do not market the EXE as fully signed before this step.

13. INSTALLATION PROCESS (FINAL STEPS)
--------------------------------------

Fresh server installation:

1. Copy TablePlay-Setup-v2.5.6.exe and its .sha256 file to the restaurant PC.
2. Verify the SHA-256 before running it.
3. Right-click the installer and choose Run as administrator.
4. Enter the restaurant name, Admin email, and a strong unique Admin password.
5. Click Install and wait for database, services, apps, and firewall setup.
6. Click Launch TablePlay and sign in as Admin.
7. Complete Admin > Setup: identity/logos/tax, tables, staff, apps, and pairing.
8. Connect all devices to the same Private Wi-Fi network.
9. Download Staff Windows/Android and Customer Android from the portal/QR page.
10. Pair each Customer tablet by scanning its table's single-use QR.
11. Run one complete test order through Counter, Kitchen, Waiter, games, bill,
    cash payment, receipt, and table closure.
12. Create and verify the first backup before serving real customers.

Regular server update/repair:

1. Create a verified Server Manager backup.
2. Run the newer TablePlay-Setup.exe as administrator.
3. Choose Upgrade / Repair; do not uninstall for a normal update.
4. Let migration, release publishing, service restart, and health check finish.
5. Confirm Admin login, device connectivity, menu photos, and one test order.

App installation/update:

1. Open Server Manager > App QR codes or Admin > App Updates.
2. Android: download the matching APK, allow installation from this local
   source when prompted, and install over the existing app.
3. Do not uninstall first; matching package ID/certificate preserves app data.
4. Windows: download the Staff ZIP/installer through the portal/updater and use
   Download and Restart when offered.
5. Confirm Staff login and Customer pairing remain saved after the update.

Offline activation:

1. Upgrade/install the restaurant server using TablePlay-Setup-v2.5.6.exe.
2. On the restaurant server, open Admin > License and download the .tpr request.
3. Transfer the .tpr file to the secured Super Admin computer by USB.
4. Open Super Admin > Restaurant Customers > Offline activation.
5. Select the customer subscription, upload the .tpr, and issue the license.
6. Download the generated .tpl file and transfer it back by USB.
7. On the restaurant server, import the .tpl from Admin > License.
8. Confirm the expected plan, status, limits, and expiry are displayed.
9. Never copy the Cloud .env or private signing key to a restaurant computer.
